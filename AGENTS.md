# AGENTS.md

Context for anyone (human or agent) changing this repo.

skagent is an ssh-agent for FIDO2 `sk-ssh-ed25519@openssh.com` keys created with `verify-required`. It caches the FIDO2 PIN for a bounded time, while the authenticator still requires a touch for every signature. Read `docs/design.md` before changing behavior. `docs/research/` holds the source-level findings the design is based on.

## layout

- `flake.nix`: flake-parts, numtide devshell, treefmt-nix, nci (nix-cargo-integration). The nci project is called `workspace` so it doesn't collide with the `skagent` crate in `nci.outputs`.
- `rust-toolchain.toml`: the toolchain nci builds with and the devshell provides (incl. rust-analyzer + rust-src from the same release). It's pinned through `flake.lock`.
- `Cargo.toml`: workspace, shared dependency versions and shared lints.
- `crates/skagent`: the agent (lib, the `skagent` binary and `age-plugin-skagent`, which uses nothing of the lib). `#![forbid(unsafe_code)]`. `signer.rs` takes a request to its security key's answer, for any `Job`: signing with an SSH key, or deriving an age identity's secret (`signer/age.rs`, which also creates identities). `age.rs` holds the age identities and remembers them in `$XDG_STATE_HOME/skagent/age.toml`; `peer.rs` tells who is on the socket for age requests (skagent's plugin or command line, by their executable; anything else is refused); the age requests are handled in `agent.rs`. Batches of decryptions: `batch.rs` is their state machine over explicit time and processes (who is a member, the kept seeds, every way a batch ends), `ancestry.rs` proves that a process descends from another (`/proc` and pidfds behind a trait), `signer/batch.rs` keeps the batches next to the PINs and watches each one (time limit, notification), `batch_tool.rs` is `skagent batch` (a child subreaper that runs the command; not hardened, since the command would inherit it). `notify.rs` shows touch notifications and a batch's standing notification with its Stop button. `bindings.rs` decides which device a request goes to (plug-in, pairing, YubiKey serial, touch, or wait for a plug-in) and remembers bindings with a serial or a pairing in `$XDG_STATE_HOME/skagent/bindings.toml`. `identities.rs` holds the keys and remembers those added on this machine without a lifetime or destinations in `$XDG_STATE_HOME/skagent/keys.toml`; `state_files.rs` writes skagent's state files (private, atomic). `pairing.rs` explains the pairing (trust on first use, then a silent challenge before any typed PIN) and verifies the challenge. `routing.rs` holds per-device/per-credential locks, waiting for a plug-in and exclusive touch selection.
- `crates/skagent-secret`: `SecretBuffer`, locked/guarded/zeroizing memory for PINs and passphrases, optionally in `memfd_secret(2)` memory (one backend per process, fixed by the first buffer; choose it before any secret exists). A single buffer can ask for a backend of its own (`from_slice_in`, `strongest_backend`): a batch's seed does. Its `unsafe` is confined to `src/mapping.rs`.
- `crates/skagent-fds`: descriptors the agent gets from elsewhere or keeps to itself: adopting the sockets systemd passes (socket activation; the one for age requests is named `age`), `inherit_stdio_only` for spawned prompts (libfido2 opens hidraw without `O_CLOEXEC`), and a pidfd of a connection's peer (`SO_PEERPIDFD`). Spawn every child of the agent through `prompt::prompt_command`. Its `unsafe` is confined to `src/activation.rs`, `src/children.rs` and `src/peer.rs`.
- `crates/skagent-fido`: safe wrapper over libfido2 (via `libfido2-sys`, bindgen against the system headers). Its `unsafe` is confined to `src/raw.rs`. Only `/dev/hidraw*` devices are used; libfido2 also lists YubiKeys over `pcsc://`. `src/pairing.rs` creates, finds and challenges skagent's pairing credential (relying party `skagent:pairing`). `src/yubikey.rs` reads YubiKey serials with Yubico's `READ_CONFIG` vendor command over hidraw itself (libfido2 can't send vendor commands): only while libfido2 has the device closed, under the device lock (`routing::Serials`).
- `crates/skagent-age`: age's post-quantum recipient (`age1pq1…`, stanza `mlkem768x25519`) for a key derived from a security key (`docs/age.md`): recipient and identity strings, stanzas validated as the age specification asks, the seed derived from a security key's hmac-secret answer, X-Wing (ML-KEM-768 from `libcrux-ml-kem`, X25519) and HPKE's base mode. No I/O, no randomness of its own, no `unsafe`. Its test data (`tests/data/README.md`) comes from age's test suite, the X-Wing draft and stock age; the salt label and the HKDF `info` in `src/seed.rs` decide every identity's recipient and must never change.
- `crates/skagent-age-plugin`: `age-plugin-skagent` as a library: age's plugin protocol (`ipc.rs`), `identity-v1` (asks the agent for each file's key, `identity.rs`) and `recipient-v1` (encrypts to the recipient an identity names, without the agent, `recipient.rs`). It never holds a long-term secret and must not depend on `skagent` or `skagent-fido`: the binary stays free of libfido2. It stays dumpable, so the agent can read its executable. Its protocol parts are public for the standalone plugin: `identity::collect` (what the age client hands over), `identity::error`, `ipc::request_secret` (a secret from the client into a `SecretBuffer`) and `ipc::show`.
- `crates/skagent-age-standalone`: `age-plugin-skagent` for systems without the agent (an initrd, a rescue system), which asks the security key itself (`docs/age.md`, the standalone plugin). `flow.rs` is `identity-v1` key first: one PIN, each of the key's credentials derived once and tried on the file, behind the trait in `key.rs` so it is tested with a key that isn't one; `device.rs` is the real key (`skagent-fido`); `stdio.rs` reads and writes the age client's end through the descriptors, wiping what was read; `watch.rs` cancels the request on the key when the client goes away or the process is told to end. No tokio, nothing of the agent's. Its binary is `skagent-age-standalone` (the agent's plugin has the name `age-plugin-skagent` in the same workspace) and is installed as `age-plugin-skagent` by `packages.age-plugin-skagent-standalone`, never next to the agent.
- `crates/skagent-popup`: the protocol between the agent and its popup (`--popup`, `skagent-pinentry`): JSON state messages to the popup, text intent lines back, PINs decoded into `SecretBuffer`s. Shared by both sides, so it stays free of GUI and libfido2 dependencies. The agent side is `crates/skagent/src/popup.rs`. `src/style.rs` holds the popup's style: the design's light and dark presets, the `[popup]` overrides of the configuration and how unset colours are mixed from changed ones. Its colour names are repeated in `nix/home-manager.nix`; `checks.home-manager-options` runs `skagent check-config` on a file with all of them.
- `pinentry/`: `skagent-pinentry`, the popup (GPUI, design B+ in `docs/pinentry.md`). A Cargo workspace of its own with its own lockfile and lints, so GPUI's ~650 dependencies stay out of the agent's. GPUI comes from Zed's repository at a pinned rev; its `[patch.crates-io]` mirrors Zed's and changes with the rev. `src/screen.rs` turns a protocol state into the copy and layout (no GUI, tested); `src/ui.rs` draws it; `src/pin.rs` keeps the typed PIN in a `SecretBuffer`; `--preview SCREEN --theme light|dark` renders the fixtures in `src/fixtures.rs`; `src/fonts.rs` loads the fonts the Nix package bundles; `src/rendering.rs` is what the popup draws with (`[popup] renderer`): `auto`, a GPU if one takes the window and else the CPU, as GPUI chooses by itself; `gpu`, never the CPU; `cpu`, Mesa's lavapipe and no GPU driver loaded. GPUI needs Rust newer than the agent's MSRV. Packaged by `nix/pinentry.nix` (`buildRustPackage`: nci builds a project from its own directory, and this one reaches into `crates/`); update its `cargoHash` whenever `pinentry/Cargo.lock` changes. `checks.licenses-pinentry` (`nix/pinentry-licenses.py`) fails if the popup links a crate that isn't permissively licensed: Zed's repository also holds GPL and AGPL crates.
- `crates/skagent-testkey`: **test-only** virtual FIDO2 key on uhid (soft-fido2, AGPL-3.0). Used inside VM tests only. `checks.license-boundary` (`nix/license-boundary.nix`) fails if a shipped crate ever reaches it or soft-fido2 through `Cargo.lock`; add new shipped crates to its `shippedCrates`. The same walk is `checks.standalone-dependencies`: nothing of the agent's (tokio, zbus, ssh-agent-lib, tracing, clap, the agent itself) is reachable from `skagent-age-standalone`. `checks.plugin-libraries` (`nix/plugin-libraries.nix`) looks at what the two age plugins link: the agent's the C runtime alone, the standalone one libfido2 besides.
- `nix/tests/`: NixOS VM tests (end to end, real OpenSSH tools against the real binary). `common.nix` has the shared helpers (stub key writer, askpass and pinentry that log prompts, uhid/hidraw setup, a private session bus with a fake notification service that records every call and, like the ones on desktops, closes a notification whose button was pressed).
- `nix/screenshots/`: `nix build .#screenshots` draws every state of the popup with skagent-pinentry itself in a VM (headless sway, the states as protocol lines in `render.py`), light and dark, cut out with transparent corners, plus the sheets, the styled popups from `themes/*.toml` and the README's one picture (`readme/skagent-popup.png`: four light popups above four dark ones, each row from the preset to the styles; `README_ROWS` says which). Not a check. Add a state's variants to `render.py` when the popup learns one, and look at the sheets after changing its layout or words: a line that is too long shows there.
- `nix/age-check.sh`: `nix run .#age-check`, a guided check of age identities and batches against a real security key (`docs/age.md`, checking with a real key). It reads the agent's log for its verdicts: keep the messages it greps for, or change both (`checks.vm-age-check` notices).
- `nix/home-manager.nix`: the home-manager module, exported as `homeModules.default` (with the packages defaulting to this flake's). The popup asks for PINs unless the configuration names another prompt (`askpass`, or a `pinentry.package` of its own, which the module tells from the option's default by its priority) or sets `popup.enable = false`. The `home-manager` input is for that output and its VM test.
- `crates/skagent/src/config.rs`: the configuration file (`--config`, default `$XDG_CONFIG_HOME/skagent/config.toml`): labels and emoji per SSH key, names per YubiKey serial, the popup's style. Nothing secret. Unknown settings are refused, except in `[popup]`: style settings that can't be used are logged warnings, so a typo in a colour can't stop the agent. `skagent check-config` fails on both. home-manager generates the file from `services.skagent.keys`, `securityKeys` and the `popup` style options, checks it with `skagent check-config` while building, and links it to `~/.config/skagent/config.toml` too.
- `clippy.toml`: proper names allowed without backticks in doc comments.
- `.github/workflows/check.yml`: every check but the popup's on pull requests, VM tests included (GitHub's Linux runners have KVM). `.github/workflows/pinentry.yml`: the popup's checks (`*-pinentry`), only when the popup or what it shares with the agent changes; list new shared paths there. Actions are pinned by commit SHA; update the SHA and the version comment together.
- `docs/design.md`: architecture, PIN cache rules, threat model. `docs/research/`: findings with source references. `docs/macos.md`: the plan for macOS support (not implemented yet). `docs/pinentry.md`: the plan for skagent's own popup (skagent-pinentry); `docs/research/popup-rendering.md`: what it draws with and why it doesn't try to keep to one GPU of two, and why the agent waits for `SHOWN`. `docs/age.md`: the plan for decrypting age files (not implemented yet); its findings are `docs/research/hmac-secret.md` (with `hmac-secret-check.sh`, a check to run against a real key) and `docs/research/age.md`.

## rules

- Conventional commits with a scope: `chore(nix): ...`, `docs(research): ...`, `docs(design): ...`, `feat(agent): ...`, `feat(fido): ...`, `feat(cli): ...`, `fix(agent): ...`, `test: ...`, `test(vm): ...`. Commit small and often.
- Write pedantic, deliberate Rust. Correctness and maintainability take priority over speed of implementation.
- Never use `unwrap`, `expect`, `panic!`, `todo!`, `unimplemented!`, `unreachable!`, indexing/slicing that can go out of bounds, unchecked arithmetic, or anything else that can unexpectedly terminate a production execution path. The workspace lints deny all of these (`Cargo.toml`, `[workspace.lints.clippy]`). Don't `#[allow]` them away; restructure the code instead.
- Every Rust crate root must carry `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic)]`. That includes `lib.rs`, `main.rs` and every integration test file, since each one is its own crate.
- Propagate errors with `anyhow` and attach actionable context that names the failed operation and the resource involved: `.with_context(|| format!("binding agent socket {}", path.display()))`, not `.context("failed")`.
- Argument parsing: `clap` with derive.
- Tests live in separate files (`crates/<crate>/tests/*.rs`), never in inline `#[cfg(test)]` modules. Logic that needs tests is exposed through the library crate.
- End-to-end behavior is tested in NixOS VMs (`nix/tests/`) in addition to the Rust tests. Anything that touches sockets, permissions, process state or OpenSSH interop needs a VM test.
- `unsafe` is denied workspace-wide (`deny`, so it can be lifted per module). Only `skagent-secret/src/mapping.rs` (raw mappings), `skagent-fido/src/raw.rs` (libfido2 FFI) and `skagent-fds/src/{activation,children,peer}.rs` (adopting descriptors, a pre-exec hook, a socket option rustix lacks) allow it, with `#[allow(unsafe_code)]` on their `mod` item, never at a crate root. Every block holds one unsafe operation with its own `// SAFETY:` comment (clippy's `multiple_unsafe_ops_per_block` and `undocumented_unsafe_blocks` deny the rest) and stays behind a safe API. All other crate roots carry `#![forbid(unsafe_code)]`.
- Terminal output must respect the user's terminal colors: use the `colored` crate with the basic ANSI colors only (no truecolor/256-color, no backgrounds), honor `NO_COLOR`, and disable color when the stream isn't a terminal. Don't over-color. Use color to highlight what matters, consistently: red = error, yellow = warning, bold = the value the user has to act on.

## known ssh-agent-lib behavior

- Unknown message types (e.g. the SSH1 `REMOVE_ALL_RSA_IDENTITIES` = 9 that `ssh-add -D` still sends) fail to decode, and the library drops the connection instead of answering `FAILURE`. `ssh-add` ignores this for the SSH1 message.
- Every refused request (default `Session` methods) is logged at `ERROR` by the library. That's noisy but contains no secrets.
- `listen()` ends on the first `accept` error. `PeerCheckedListener` retries transient errors so that can't happen for resource exhaustion.
- The codec buffers whatever length a message announces (up to 4 GiB), and decoders aren't bounded by the frame (extension details are the rest of the read buffer). `PeerCheckedListener` hands out `frames::BoundedStream`s, which end a connection whose message announces more than OpenSSH's 256 KiB.

## destinations

- `destination.rs` follows OpenSSH's ssh-agent rules for `session-bind@openssh.com` and `restrict-destination-v00@openssh.com`; check changes against `ssh-agent.c` (`identity_permitted`, `process_ext_session_bind`, `process_sign_request2`). Decode those messages with the strict decoders there, not ssh-agent-lib's types: they drop reserved fields and don't check trailing data, which would accept constraints skagent doesn't understand.
- Anything skagent can't decode must only ever narrow where a key may be used: a failed bind hides constrained keys, unknown host key types and CA entries never match.
- Text from signed data (users, namespaces) and key comments is shown to the user; pass it through `display::shown` (`Purpose`, `signer::describe` do), it can come from another machine.

## age

- Read `docs/age.md` before changing anything about age identities. The salt label and the HKDF `info` (`skagent-age/src/seed.rs`) decide every identity's recipient: never change them. The files are age's own format: nothing here may produce a stanza stock age wouldn't.
- An identity's private key exists only while one file is decrypted: the security key's answer and the seed are `SecretBuffer`s, dropped before the reply is built. Only the file key leaves the agent, at most one per request (`Seed::unwrap` stops at the first stanza that opens).
- Never ask a security key for hmac-secret with `up=false`, and never use an answer whose flags lack the touch or the verified PIN (`skagent-fido/src/age.rs`). Never create an age credential as a side effect, and never with a user id the key may already hold: that replaces a credential and destroys its key.
- The socket for age requests answers skagent's own programs only, and each only what it may ask: the plugin for file keys, the command line to create and list. It answers nothing of the ssh-agent protocol, and the ssh-agent socket answers no age request. A connection that binds an SSH session is forwarded and gets nothing more.
- Replies to the plugin carry reason codes, never text about this machine.
- A security key answers a touch that never came with `OPERATION_DENIED`, the code for a refused one (CTAP, and a YubiKey 5.8 after 28 s). It is `ErrorKind::TouchTimeout`; don't split it off again. The virtual key answers the same.
- What a decryption's popup says last is the agent's to decide after unwrapping (`signer::LastWord`): "Decrypted" needs a file key. A request that names an identity among several unused ones tries them in turn (`AgeIdentities::choose`, the loop in `AgentSession::unwrap`); one that names none never does.
- A notification's signals (`notify::Standing`) are read from one stream, in the order the service sent them: a service closes a notification whose button was pressed, and with a stream per signal it was luck which of the two the agent saw first: a pressed Stop was taken for a notification the user had closed, and the batch went on. A press also counts right after its notification was called closed.
- The agent's way from a request to the security key is `Signer::run` for every `Job`. A rule that holds for signatures (tickets, the retry guard, cancellation, what is cached when) must hold for decryptions because they share that code, not because it was written twice. The one exception is the standalone plugin (`skagent-age-standalone/src/flow.rs`), which has no agent to go through: it shares the derivation (`Device::derive`, `batch_salt`, `Seed`) and nothing of the way to it. A rule for the way to the key that should hold without an agent too has to be written and tested there as well.
- age and rage start a plugin once for each identity line, with that line alone, and take an `error` for the end of the decryption (`docs/research/age.md`). Don't design for a run that sees every line. The agent's plugin answers a line that names a recipient the agent has no identity for (or whose key holds another) with nothing instead of an `error` (`identity.rs`, `names_another_key`), so the agent's own line or a key file after it has its turn; the reason is in the agent's log. The standalone plugin therefore opens a file with the key at hand whichever identity the line names, and ends with an `error` when nothing opens, so the same key isn't asked again for the next line.
- The standalone plugin: never retries a PIN by itself, doesn't ask below `FEWEST_TRIES`, sends no answer to the key that no PIN has the length of, holds no PIN while it waits for a person (a missed touch wipes it and asks again), asks no key when several could hold an identity, and refuses next to an agent's socket. It reads its PIN through `stdio::ClientInput`, not `std::io::Stdin`, whose buffer would keep it.
- Identity strings of version 1 are read by initrds that are rebuilt rarely: keep emitting and reading them, like the salt label and the HKDF `info`.
- A batch (`skagent batch`) is the one place a seed outlives a request. It is kept only after a request whose prompt named the batch (`Request::Batch`, also on the touch screen), only for processes proven to descend from the batch's tool (`ancestry::descends`: every process pinned by a pidfd, the parent's pid read again after pinning it, everyone checked to exist at the end), and only while PINs may be cached. The seed is read under the signer's state lock and never copied out of the batch.
- Whatever evicts all PINs goes through `Signer::evict`, which ends every batch under the same lock. A batch that ended keeps nothing again: a new one needs a new `skagent batch`. Add new ends to `batch::Ended`, and keep `batch.rs` free of I/O: time and processes come in as arguments.
- Requests on the ssh-agent socket are forwarded ones, bound to an SSH session or not. Without `--age-forwarding` that socket knows no age request; with it, `age-unwrap@skagent` alone. They are never served from a batch, can't open one, and can't create or list identities. Who asks comes from `SessionBindings::forwarded_to`, and every prompt has to say it, the popup's touch screen included.

## secrets

- The PIN and anything derived from it never get logged, `Debug`-printed or written to disk. Store secrets in `skagent_secret::SecretBuffer` (locked, guarded, zeroized, redacted `Debug`, no `Clone`), never in `String`/`Vec<u8>` longer than unavoidable, and compare them with `constant_time_eq`.
- The popup (`pinentry/`): the typed PIN is in one piece only in `PinInput`, a `SecretBuffer`. Each key comes from GPUI as an ordinary `Keystroke`, which can't be helped; never give GPUI more of it: no text field of its own, no input handler, no key bindings (it collects pending keystrokes for those), nothing logged. The process hardens itself first (`skagent_secret::harden_process`), answers go to the pipe through the descriptor (`answers.rs`), not through `Stdout`'s buffer. `docs/pinentry.md`, the typed PIN's way, has what was read in GPUI at the pinned rev: read it again when the rev changes.
- What the popup draws with is `[popup] renderer`, and the popup never quietly draws with something else. `auto` (the default) leaves the graphics loaders alone: GPUI looks at every driver installed and takes a GPU before the CPU, like any program. `gpu` is the same and `cpu` its opposite, and `rendering::check` fails the popup, and the request with it, when the window ended up with what they exclude. `cpu` also loads no GPU driver: `rendering::prepare` gives the Vulkan loader and libglvnd their orders through the popup's own environment (lavapipe alone, no layer, no EGL vendor; and unset, what a session would tell the loader past that: its own list of drivers, layers forced on) and starts the program again if it has to, before anything else; keep it first in `run`. A variable of the loaders that can add a driver or a layer belongs in `rendering::ON_THE_CPU`. `vm-pinentry` fails when a stand-in driver is loaded with `cpu`. Don't make the popup pick one GPU of several by itself or promise to leave one alone: what a Vulkan driver opens to find its GPU changes between Mesa releases (`docs/research/popup-rendering.md`, where the two designs that tried are). What keeps a key from blinking for a prompt a broken driver never drew is `SHOWN` (below), whatever draws the window.
- Nothing that needs the user to see the popup happens before the popup says `SHOWN`: use `PopupSession::show_visibly` (or `Shower::show_visibly`) for a state that comes before a touch or an answer, `show` only for what is merely read (results, waiting for a plug-in). A popup that doesn't say it in `SHOW_TIMEOUT` is ended with its session and never handed to the next request. The popup says `SHOWN` after the fade-in and the display server's next frame request (`ui.rs`, `tell_shown`): not earlier, a state that is drawn isn't a state that is seen.
- `WAYLAND_DEBUG` makes libwayland-client write every key it gets to stderr, which for a prompt is the agent's log. `prompt::prompt_command` takes it out of every prompt's environment, and the popup refuses to take a PIN with it set. `vm-pinentry` runs the agent with it and finds no `wl_keyboard` in the journal.
- ssh-agent-lib logs every request at `debug` level (key handles, lock passphrases). Its `debug`/`trace` output must stay filtered no matter what log filter the user passes.
- libfido2 writes every HID message to stderr whenever `FIDO_DEBUG` is set, whatever `fido_init` gets. `skagent_fido::ensure_debug_off` refuses device access then, and `serve` refuses to start; keep every new entry point into libfido2 behind it.
- Fail closed: if a safety check can't be performed (peer credentials, retry counter, socket ownership), refuse the operation. If logind monitoring or the sleep delay inhibitor fails, disable caching until it recovers; uncached signing is still allowed.
- Eviction must revoke signing tickets as well as wipe cache entries. A pending prompt or late assertion must never refill an evicted cache. Global evictions revoke every ticket; removing or expiring one identity (`Signer::forget`) revokes only that credential's tickets, so unrelated signatures keep going.
- Every agent request locks its state through `Shared::state_now`, which removes expired identities with their PINs and bindings, and uses the returned `now` for all lookups under that lock.
- The logind signal loop must keep polling every stream: zbus blocks its socket reader on a full subscription queue. Any method call inside the loop needs a short timeout, and proxies use `CacheProperties::No`.
- Blocking device operations must stay cancellable (`cancel.rs`): assertions run under a `DeviceInterrupt`, selections check an `Abandoned` flag, and long agent requests run under `Hangup::unless_closed`. Cancelling never replaces the ticket check after the worker returns. Only waiting phases (device work, selection, prompts, enumeration) may be cut short by a hangup; authorizing a request and committing its result always run to the end, and functions that change several pieces of state take every lock first and then change everything without another `.await`, so a dropped future can never leave half a change behind. The only libfido2 call allowed concurrently with another on the same handle is `fido_dev_cancel`, through `CancelSlot`; don't call `fido_dev_set_timeout`, `fido_dev_set_pin` or `fido_dev_force_*` after open (see the SAFETY comment there).
- Never send a PIN to a device that isn't known to hold the credential. Wrong-device PIN attempts cost that device a retry, and `verify-required` credentials can't be found by a silent probe (see `docs/design.md`, multiple keys). The one exception is deliberate: a key without a binding, with exactly one device connected, uses that device, so the PIN the user types for that key goes there (like OpenSSH). Cached PINs only ever go to the device they were verified on.
- Don't hold the agent state lock across device operations or prompts; they block for up to ~35 s. Per-device locks must travel with the device into blocking workers, never be dropped with an async caller while hardware is still in use.
- Resident loading must preserve existing identity constraints and stage all PIN copies before committing. Only successful PIN-authenticated enumeration may prime caches; never serialize a PIN into an agent extension.
- Only keys added on this machine (no session bind on the connection) without a lifetime or destination constraints are remembered across restarts; keys added through a forwarded agent never change `keys.toml`, and adding a key again with a lifetime or destinations forgets it. Removal forgets it too.
- PIN eviction preserves bindings; identity removal drops them, the remembered ones in the file included. A stale binding requires touch selection, not automatic substitution of another connected key; only a device proving the binding's pairing, or for an unpaired YubiKey a plug-in reporting its serial, counts as the same key. Its cached PIN doesn't follow it. A device claiming a paired key's serial without the proof, or two devices claiming one key, get no PIN.
- Never create a pairing credential when looking for one failed: creating replaces the key's old one, and every machine paired with it would refuse the key. Pairing never fails the request it follows.
