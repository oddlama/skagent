# skagent-pinentry: plan

Milestone 11. A popup of skagent's own that takes the user through one
signature: PIN, then touch, then done. It also handles the errors around it:
a wrong PIN, the wrong YubiKey plugged in, a key that wants to be re-plugged.
Its visual design ("B+") is maintained outside this repository; this document
covers behaviour and what skagent has to provide. Nothing here is implemented
yet unless a section says so.

## decisions

- **Own process, own protocol.** `skagent-pinentry` is a separate binary (GPUI),
  spawned by the agent. GPU drivers, fonts and a Wayland client never enter the
  process that holds the cached PINs. It's not an Assuan pinentry: the agent
  decides what to show and the popup only renders it and reports what the user
  did. Stock pinentries (`--pinentry`, `--askpass`) keep working as before.
- **Wayland first, compositor-agnostic.** A layer-shell overlay with exclusive
  keyboard focus where the compositor offers it (sway, Hyprland, niri, river,
  labwc, KDE), an ordinary window elsewhere. No compositor-specific code.
- **YubiKeys by serial number.** Bindings name the YubiKey by its serial, so a
  replugged key is recognized without a selection touch, and bindings survive
  agent restarts. Cached PINs stay tied to one plug-in.
- **One popup at a time.** Requests queue for the popup. A running popup is
  reused for the next request instead of closing, and shows how many wait.
- **Unverified hosts** show a short host key fingerprint.
- **Configuration** lives in `~/.config/skagent/config.toml`, generated by
  home-manager options.

## architecture

```
skagent serve ── stdin: states (JSON lines) ──> skagent-pinentry (GPUI)
              <─ stdout: intents ──────────────
```

- **Agent = controller, popup = view.** The agent owns the state machine,
  because it sees the devices, the PIN retries and the requests. It sends the
  complete state to show; the popup sends back only `pin`, `cancel` and
  `retry`. The PIN line is read into locked memory like pinentry's `D` line.
  State messages never contain secrets.
- **Session.** The agent starts the popup for the first request that needs it,
  sends every state of that request, and moves straight on to the next queued
  request when one is done. It closes the popup (EOF on stdin) when the queue
  is empty. A popup that exits or answers garbage cancels the request.
- **Every signature goes through the popup** while it's configured: its touch
  and done states replace the desktop notification. Requests run one after the
  other; signing on two keys at once becomes sequential.
- **The popup** has a `--preview <state> --theme light|dark` mode that renders
  fixtures, for comparing against the design and for screenshot tests.

## what the agent has to learn

- **YubiKey serials.** YubiKeys report their serial over the FIDO interface
  through Yubico's vendor command `READ_CONFIG` (CTAPHID `0xC2`, as used by
  `ykman`). libfido2 can't send vendor commands, so `skagent-fido` sends it over
  hidraw itself, under the device lock, once per plug-in. Other authenticators
  have no serial: they keep plug-in bindings, fallback names and no wrong-key
  detection.
- **Bindings by serial,** persisted in `$XDG_STATE_HOME/skagent/bindings.toml`
  (a hash of application and key handle, mapped to a serial; nothing secret).
  A connected device reporting the bound serial is that YubiKey. If it isn't
  plugged in, the request waits for it (`wrong-key`, `no-key`) instead of
  falling back to selection. The PIN is never sent to another YubiKey.
- **PIN retries within a request.** A wrong PIN keeps the popup open and asks
  again, each attempt typed by the user. `PIN_AUTH_BLOCKED` waits for a
  re-plug of the same serial; `PIN_BLOCKED` ends the request.
- **Host names.** From the key's destination constraint, else by looking up
  the verified host key in `~/.ssh/known_hosts` (`HashKnownHosts` entries
  can't be reversed), else a short fingerprint (`host SHA256:+DiY3…`).
- **Names and emoji** from the config file: per SSH key (fingerprint) an emoji
  and a label, per YubiKey (serial) a name.
- **Touch timeout.** The countdown needs the key's own timeout; YubiKeys seem to
  give up after about 15 s. To be measured on hardware.

## states

The design covers `pin`, `wrong-pin`, `touch`, `wrong-key`, `replug` and
`done`. These still need a design; each entry says when it appears, what it
has to show and where it leads.

1. **`select`: pick the YubiKey by touch.** When a key has never been used (no
   YubiKey is known for it) and several security keys are plugged in.
   `verify-required` keys can't be found without the PIN, so the user has to
   choose; every plugged-in key blinks. Shows the SSH key (emoji, label), that
   the user should touch the YubiKey holding it, and how many keys are plugged
   in. A 30 s countdown. ✕ cancels. Leads to `pin` (or `touch`). Because
   signing then needs a *second* touch, the following `touch` state should make
   that clear ("once more"). The same state is used by `skagent load` ("touch
   the YubiKey to load from"), without an SSH key.
2. **`no-key`: nothing plugged in.** Two variants: the YubiKey is known ("Plug in
   Desk 5C NFC", like `wrong-key` without a wrong key) or not ("Plug in the
   YubiKey with github-work"). Waits; ✕ cancels. Leads on automatically when a
   key appears.
3. **`locked`: PIN blocked** (no tries left). Shows the YubiKey's name and that
   only a reset helps (it wipes the key). Only ✕.
4. **`timeout`: no touch in time.** Shows the YubiKey, "Timed out", and one
   action, try again (Enter). The accepted PIN is kept for the retry, so it
   isn't asked again.
5. **`new-pin`: the key wants a new PIN first** (`forcePINChange`, for example
   right after provisioning with a temporary PIN). Shows the YubiKey's name and
   that the PIN has to be changed (`ykman fido access change-pin`). Only ✕.
   Changing the PIN inside the popup could come later.
6. **`load`: enter the PIN to load resident keys** (`skagent load`). There's no
   SSH key yet, so no emoji or label: the anchor is the YubiKey. PIN field,
   then no touch (credential management needs none), then a `done` variant
   saying how many keys were loaded. `wrong-pin`, `replug`, `locked` and
   `new-pin` apply as well.
7. **Queue indicator.** While other requests wait, the popup shows how many
   (and possibly their keys' emoji). When the current request is done, the
   popup crossfades to the next one instead of closing.
8. **`failed`: anything else.** The key was unplugged mid-signature, a transport
   error, the signature didn't verify. A short reason; ✕ or auto-close.

No design needed: when the agent revokes a request (screen lock, `skagent
forget`, the client hung up), the popup closes, or moves to the next request.

### subtitle copy per request kind

| Request | Subtitle |
| --- | --- |
| SSH login, host known | `github.com` |
| SSH login through a forwarded agent | `github.com via jump` |
| SSH login, host not resolvable | `host SHA256:+DiY3…` |
| SSHSIG, namespace `git` (commits, tags) | to be decided, e.g. `Git signature` |
| SSHSIG, other namespace | e.g. `Signature for "file"` |
| anything else | e.g. `Unknown request` |

## steps

1. **Config file and home-manager options.** Labels already improve the stock
   prompts.
2. **YubiKey serials** in `skagent-fido`, and the test key answering
   `READ_CONFIG`.
3. **Popup protocol and session** in the agent, with a scripted fake popup for
   the VM tests.
4. **`skagent-pinentry`** with the designed states and the preview mode.
5. **Bindings by serial,** persistence, the waiting states, PIN retries within a
   request.
6. **Host names,** request kinds, the remaining states, touch timeout.
