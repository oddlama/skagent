# what the popup draws with, and whether it is on the screen

Findings behind two rules of skagent's popup: it draws on the CPU and loads no GPU driver, or that of the display server's GPU alone if told to and if that is the only GPU, and the agent asks for nothing before the popup says a prompt is on the screen. Both come from one afternoon on one machine. Sources: that machine's journal, GPUI at `6983685` (`gpui_wgpu/src/wgpu_context.rs`, `gpui_linux/src/linux/wayland/window.rs`, `gpui/src/window.rs`), wgpu `cddb2f5` (30.0.0), Vulkan-Loader 1.4.363 (`loader/loader.c`, `docs/LoaderInterfaceArchitecture.md`; its other variables and its settings file at `vulkan-sdk-1.4.335.0`: `loader/loader.c`, `loader/loader_environment.c`, `loader/settings.c`), libglvnd 1.7.0 (`src/EGL/libeglvendor.c`), Mesa 26.2.5 (the paths below), Linux 6.18 (`drivers/gpu/drm/nouveau/nouveau_drm.c`, `drivers/gpu/drm/amd/amdgpu/amdgpu_kms.c`), NVIDIA's open kernel modules 595.58.03 (`kernel-open/nvidia-drm/nvidia-drm-drv.c`).

## what GPUI loads to draw a window

- **Every driver there is.** GPUI creates a wgpu instance for Vulkan and GL and enumerates all adapters before it picks one. For Vulkan the loader opens the library of every driver manifest it finds (`loader_icd_scan`, `loader_scanned_icd_add`); for GL, libglvnd loads every EGL vendor library (`LoadVendors`).
- **Then it picks:** an adapter named by `ZED_DEVICE_ID`, else the one the Wayland compositor draws on (the main device of its dmabuf feedback), else a discrete GPU before an integrated one, Vulkan before GL; the first that can configure the window's surface.
- **So a second GPU is always touched,** whichever is picked. Seen in a VM with a stand-in driver and vendor library that leave a file when loaded: every start of the popup loaded both, 5 of 5 (`checks.vm-pinentry`, with the popup's own environment taken out).
- **A sleeping GPU wakes for it.** On a laptop with an Intel and an NVIDIA GPU (NVIDIA's open kernel module 595.104.02, runtime power management), both popups that started with the GPU asleep were followed by the kernel's `nvidia 0000:01:00.0: Enabling HDA controller` before their PIN was typed. That the popup calls into that driver is in the second crash below: its call trace starts at an `ioctl` of `skagent-pinentr`.

## what a Vulkan driver opens to find its GPU

Read after `renderer = "gpu"` was written, which let the display server's GPU draw next to a second one as long as the two had different Vulkan drivers. That rested on a guess: a driver opens only the devices of its own vendor. In Mesa 26.2.5, the Mesa of the machine below, it isn't so, and for Intel's driver not since 26.1.

- **Every Mesa driver is shown every GPU.** `enumerate_drm_physical_devices_locked` (`src/vulkan/runtime/vk_instance.c`) lists all DRM devices (`drmGetDevices2`, which reads sysfs and opens nothing) and hands each to the driver's `try_create_for_drm`. What the driver does with a device that isn't its own is the driver's business:
  - **Intel's (`intel_icd`) opens it.** `anv_physical_device_try_create` (`src/intel/vulkan/anv_physical_device.c`) starts with `open(path, O_RDWR | O_CLOEXEC)` on the render node, asks the device whether it is a virtio one (`intel_virtio_init_fd`), and only then looks at the bus and the PCI vendor. Every render node of the machine is opened.
  - **Qualcomm's (`freedreno_icd`) opens it** and asks for its driver's name (`tu_physical_device_try_create`, `src/freedreno/vulkan/tu_knl.cc`).
  - **AMD's (`radeon_icd`) looks first:** `create_drm_physical_device` (`src/amd/vulkan/radv_physical_device.c`) goes on only for a PCI device of AMD or of virtio, or any device on the platform bus, and opens that.
  - **Intel's for old GPUs (`intel_hasvk_icd`) looks first** as well, at the PCI vendor (`src/intel/vulkan_hasvk/anv_device.c`). It is selected together with `intel_icd`, so that doesn't help.
  - **Nouveau's (`nouveau_icd`)** opens the node and then checks that its driver is nouveau (`nouveau_ws_device_new`, `src/nouveau/winsys/nouveau_device.c`). What is checked before that call wasn't read.
- **Lavapipe looks at no GPU.** `lvp_enumerate_physical_devices` (`src/gallium/frontends/lavapipe/lvp_device.c`) asks for software devices only, and Mesa's window system code (`src/vulkan/wsi/wsi_common.c`, `wsi_common_wayland.c`, `wsi_common_drm.c`) opens no device node. This is what drawing on the CPU rests on.
- **An open wakes a GPU that sleeps,** depending on its kernel driver. `nouveau_drm_open` and `amdgpu_driver_open_kms` call `pm_runtime_get_sync`: the GPU is powered up, and the open waits for it. NVIDIA's own module does nothing of the kind in `nv_drm_open` (it numbers the file); closing goes through `nv_drm_postclose`, which revokes modeset permissions for a device with outputs. Either way it is a call into the kernel driver of a GPU the popup has no business with. Not seen on a machine: whether the NVIDIA GPU of the laptop below stays asleep through an open.
- **So one GPU among two can't be promised.** Which driver opens what changes between Mesa releases: Intel's looked at the vendor first up to 26.0 (read in 25.0.7, 25.2.8, 25.3.6 and 26.0.6) and opens first since 26.1 (26.1.5, 26.2.0, 26.2.5), when it learned to draw through a virtio device. The popup doesn't know the Mesa it will meet: that is the system's, not the package's. The popup draws on a GPU only if it is the machine's only device that renders.

## the afternoon (2026-11-20, kernel 6.18.58)

The machine had been up for days and its memory was fragmented: page allocation failures of order 6 and 7 from 11:18 on (iwlwifi among them), with 2.4 GB free and no free block of 512 kB. Every wake of the NVIDIA GPU that day, ten of them, most caused by other programs, logged `NV_ERR_NO_MEMORY` from the driver.

| time | what happened |
| --- | --- |
| 15:25:41 | `skagent load` starts the popup; the NVIDIA GPU wakes. This time the driver fails to allocate a buffer it frees on the way back to sleep (`kccuStateLoad_IMPL: Failed to init device shared buffer`). |
| 15:26:04 | The GPU goes back to sleep: a NULL pointer dereference in `nv_free_kernel_mapping`, from `nv_pmops_runtime_suspend` (kernel oops #1). The worker dies in the middle of the driver, its state left as it was. |
| 15:28:41 | `age -d -j skagent` starts the popup. The agent has the PIN cached, sends the touch state and asks the security key, which blinks. |
| 15:28:44 | The popup's first call into the NVIDIA driver (the version check its library does when loaded) runs into what oops #1 left: a page fault in `_mapInsertBase`, on the dead worker's stack (oops #2). The kernel ends the popup's main thread, `with irqs disabled` and `preempt_count 1`: inside a spinlock of the driver. |
| 15:28:48 | The user touches the blinking key. Nothing is on the screen: the popup's process is still there, its other threads read the agent's messages, and nothing draws. The agent can't tell. |
| 15:28:56 | The agent closes the popup, which doesn't leave, and kills it after 8 s. |
| later | The same command again. The machine freezes and nothing reaches the journal: the next call into the driver waits for the spinlock that oops #2 left locked, with interrupts off. |

The crashes are the NVIDIA driver's: it doesn't survive a failed allocation while resuming. skagent's part was to call into that driver at all, for a window of 360 pixels, and to let a key blink for a prompt that wasn't there.

## what follows for skagent

- **The popup draws on the CPU** (`pinentry/src/rendering.rs`), with Mesa's lavapipe, and nothing else is loaded. The loaders take this through their environment, read when they are loaded, so the popup starts itself again with it if it has to, once (it leaves its process id in `SKAGENT_PINENTRY_STARTED_AGAIN`, and gives up if it finds its own there and the environment still differs):
  - `VK_LOADER_DRIVERS_SELECT=lvp_icd.*`: the Vulkan loader (1.3.234 or newer) skips every driver whose manifest's file name doesn't match, before it would open its library.
  - No `VK_DRIVER_FILES` and no `VK_ICD_FILENAMES`: either replaces the loader's search for drivers (`loader_get_data_files`), and the selection is made among what it names. A session that names a GPU's driver there, to pick one of two, names no lavapipe: nothing is left, and the popup has no window.
  - `VK_LOADER_LAYERS_DISABLE=~all~`, and no `VK_LOADER_LAYERS_ALLOW`: no layer is loaded either. NVIDIA's device-switching layer lives in the same library as its driver, and overlays or capture layers have no business in a PIN prompt.
  - No `VK_LOADER_LAYERS_ENABLE` and no `VK_INSTANCE_LAYERS`: the first enables a layer over the disabling, implicit or not (`loader_implicit_layer_is_enabled`; `loader_add_environment_layers`: "This can override the disable above"), the second adds its layers without a look at it ("we will always add it to the layer list").
  - `__EGL_VENDOR_LIBRARY_FILENAMES` set and empty: libglvnd then loads the vendors listed, none, instead of looking for them. wgpu is left with Vulkan.
  - `LIBGL_ALWAYS_SOFTWARE=true`, for an EGL that isn't libglvnd's.
  - Left as they are, since they can't add anything: `VK_LOADER_DRIVERS_DISABLE` (`loader_icd_scan` skips a driver that is disabled and not selected: selected wins), `VK_ADD_DRIVER_FILES` and the paths to look for layers in (more to choose from, and the selection and the disabling still apply).
- **One order isn't in the environment.** A `vk_loader_settings.json` (the Vulkan configurator, vkconfig, writes it) that orders the devices makes the loader read none of the driver variables (`loader_settings_should_use_driver_environment_variables`): every driver is loaded again. The popup can't prevent that. It warns when its window is then drawn on a GPU, which is all it can see: what draws the window, not what else was loaded.
- **With that, in the VM:** no stand-in driver or vendor library is loaded by any popup, the popup reports `llvmpipe`, and its window opens 80 to 260 ms after the first state arrives. The pictures in the README were always drawn this way.
- **What it costs:** the popup needs Mesa's software Vulkan driver (in Mesa's package on NixOS, `vulkan-swrast` or `mesa-vulkan-drivers` elsewhere), and drawing takes CPU time: 1.4 s of it over the first 3.4 s of a popup on average, starting included (69 popups of `nix build .#screenshots`, in a VM at twice the size, 720 pixels square).
- **The display server's GPU, on request** (`[popup] renderer = "gpu"`). It is the one GPU that is awake for certain, and its driver the one the desktop already depends on. The popup asks the compositor for the main device of its dmabuf feedback, as GPUI does to prefer that GPU, reads the device's kernel driver from sysfs (`/sys/dev/char/<major>:<minor>/device/driver`) and selects the Vulkan driver for it next to lavapipe: `VK_LOADER_DRIVERS_SELECT=intel_icd.*,intel_hasvk_icd.*,lvp_icd.*` for `i915`. Everything else stays as on the CPU. It keeps to the CPU if no device is named, if sysfs has no driver for the one named, if it knows no Vulkan driver for the kernel driver, and if there is any other render node here (`/sys/class/drm/renderD*`, one whose driver can't be read included), whatever its driver: see above for what a Vulkan driver opens. Each has its reason in the log, as a warning. If the GPU's driver doesn't take the window, GPUI goes on to lavapipe by itself.
- **Of that, seen:** against niri on the machine above, the popup's question is answered with device 226:128, a render node. In the VM the compositor draws without a GPU and names none; the popup, started with `--renderer gpu`, says why it draws on the CPU, and loads no stand-in driver. Reading sysfs is tested against a tree laid out like the kernel's (`pinentry/tests/rendering.rs`), not against a real one. Not seen: a window drawn on a GPU this way.
- **The agent waits for `SHOWN`** (`skagent-popup`, protocol version 2; `PopupSession::show_visibly`): the popup says when a state is on the screen, and before that no security key is asked for a touch and no answer is taken. The popup says it once the state has faded in and the display server asked for the frame after that one, which it only does for a window it shows. A popup that hasn't said so after 10 s is ended, and the request fails.
- **Seen with the real popup:** behind a lock screen (swaylock) it draws and never says `SHOWN`; the request fails after 10 s and the key is never asked.

Not looked at: a real machine with two GPUs after the change, a Vulkan loader older than 1.3.234 (the popup then warns that it draws on a GPU), an EGL library that isn't libglvnd's, and Mesa's other Vulkan drivers (`virtio_icd`, `panfrost_icd`, `broadcom_icd`, `asahi_icd`).
